# Getting the containerized API talking to Postgres

While containerizing the FastAPI app, the app couldn't reach the database at all once it was running inside Docker, even though everything worked fine running directly on the VM. Took a few rounds to sort out fully, so writing down what actually happened instead of just the final fix, since the process is probably more useful than the answer.

First run of the container just failed outright with connection refused on 127.0.0.1:5432. Makes sense once you think about it - inside a container, 127.0.0.1 means the container itself, not the host machine. Postgres is running on the VM, not inside this container, so of course there's nothing listening there. Switched the app's DB_HOST to host.docker.internal, which is the special hostname Docker provides for a container to reach its host machine. On Linux you also need to pass --add-host=host.docker.internal:host-gateway when running the container, since Linux doesn't wire this up automatically the way Docker Desktop does on Mac/Windows.

That got further but still failed, this time with connection refused again but resolving to the right IP (172.17.0.1, the docker bridge gateway). Checked what Postgres was actually listening on with ss -tlnp, and it turned out Postgres was only bound to 127.0.0.1 and ::1 - loopback only, which is the default out of the box. So even though the container could now find the host, Postgres itself was refusing anything not originating from the machine itself. Fixed by setting listen_addresses = '*' in postgresql.conf. This one needs a full restart, not just a reload, since it's a setting Postgres only reads at startup.

After that, connection attempts started actually reaching Postgres, but got rejected with "no pg_hba.conf entry for host 172.17.0.2" - a new error, and a more specific one, since 172.17.0.2 is the container's actual IP on the docker bridge network. pg_hba.conf is what decides who's allowed to authenticate once they reach the server, separately from whether the server is listening at all. Added a rule scoped to 172.17.0.0/16 (the docker bridge subnet, not 0.0.0.0/0) requiring password auth, so any container on this host can attempt to log in with a password, but nothing outside the host can.

Even after adding that line the first retry still failed with the same error. Turned out to just be a stale reload - ran systemctl reload postgresql again along with SELECT pg_reload_conf() from psql to be sure, and the next attempt went through cleanly. Worth remembering that pg_hba.conf changes need an explicit reload to take effect, and it's easy to assume a change landed when it actually didn't.

End state: container reaches Postgres over the docker bridge network using host.docker.internal, Postgres listens on all interfaces but pg_hba.conf restricts who can actually authenticate to the docker subnet plus localhost, all with password auth except the local postgres superuser socket connection, which stays on peer auth since reaching that already requires host-level sudo access.

Confirmed working end to end with a real POST to /api/payments through the running container, not just the health check, since a health check passing doesn't prove writes work.

---

Separately, worth noting how I handled seeding the in-cluster Postgres (the StatefulSet, not the VM-level one used for local dev and the SQL work). Attempted to load the same 50k-row seed.sql into it, same as the VM database, for consistency. First attempt streamed through kubectl exec -i and hit a connection timeout partway through - the long-lived exec stream through the Kubernetes API server apparently has a shorter tolerance than a direct psql connection does. No data was left half-loaded, since the whole file is wrapped in a single transaction, so it rolled back cleanly.

Second attempt used kubectl cp to copy the file into the pod first, then ran psql against it locally inside the container, avoiding the streaming issue. This one failed differently: partway through, both the readiness and liveness probes started timing out (they default to a 1 second timeout, which I hadn't overridden), Kubernetes concluded the container was unresponsive, and killed and restarted it mid-transaction. Same clean rollback, but the underlying cause was different and more interesting - the probes added to protect the database ended up being the thing that took it down under sustained write load.

I fixed the probes by adding explicit timeoutSeconds and a higher failureThreshold, giving Postgres more room to be legitimately busy without being judged unresponsive. Given that requirements/03-kubernetes-rancher.md doesn't actually call for any specific data volume in the cluster, and this was already the second unplanned detour debugging my own test data rather than the deployment itself, I made a deliberate call not to re-attempt the full 50k load and re-verify the probe fix against it. I seeded a handful of rows manually instead, enough to prove the database is real and writable for the API deployment and Rancher work ahead. The probe fix itself is applied and confirmed live in the cluster, just not stress-tested against a bulk load the assessment doesn't ask for.

---

One more real issue, this time on the API Deployment itself, not Postgres. First rollout of minipay-api showed 1 restart. Checked the pod events and found two distinct failure phases: early on, the liveness probe got connection refused, meaning nothing was listening on port 8000 yet - the app was still starting up. A bit later, the probe failed again, this time with a timeout instead of a refusal - the app was listening but not responding in time, which pointed at the /health endpoint hanging while it tried to reach Postgres.

Root cause: nothing in the deployment actually enforces that Postgres has to be up before the API starts. The Deployment and the StatefulSet are independent objects, and Kubernetes starts both as soon as their own conditions are met - there's no ordering guarantee between them by default. This time the API lost that race, got killed by its own liveness probe for being unresponsive, and came back up clean once Postgres was actually ready. Self-healing worked as designed, but it meant an avoidable minute or so of instability that a real dependency check would have prevented outright.

Fixed with an init container on the API deployment - a container that has to exit successfully before the main container starts, running a small loop of pg_isready against the postgres service every 2 seconds. Redeployed and confirmed 0 restarts and a clean health check on the first attempt, no race this time.
