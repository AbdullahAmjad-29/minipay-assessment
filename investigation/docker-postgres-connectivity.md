# Getting the containerized API talking to Postgres

While containerizing the FastAPI app, the app couldn't reach the database at all once it was running inside Docker, even though everything worked fine running directly on the VM. Took a few rounds to sort out fully, so writing down what actually happened instead of just the final fix, since the process is probably more useful than the answer.

First run of the container just failed outright with connection refused on 127.0.0.1:5432. Makes sense once you think about it - inside a container, 127.0.0.1 means the container itself, not the host machine. Postgres is running on the VM, not inside this container, so of course there's nothing listening there. Switched the app's DB_HOST to host.docker.internal, which is the special hostname Docker provides for a container to reach its host machine. On Linux you also need to pass --add-host=host.docker.internal:host-gateway when running the container, since Linux doesn't wire this up automatically the way Docker Desktop does on Mac/Windows.

That got further but still failed, this time with connection refused again but resolving to the right IP (172.17.0.1, the docker bridge gateway). Checked what Postgres was actually listening on with ss -tlnp, and it turned out Postgres was only bound to 127.0.0.1 and ::1 - loopback only, which is the default out of the box. So even though the container could now find the host, Postgres itself was refusing anything not originating from the machine itself. Fixed by setting listen_addresses = '*' in postgresql.conf. This one needs a full restart, not just a reload, since it's a setting Postgres only reads at startup.

After that, connection attempts started actually reaching Postgres, but got rejected with "no pg_hba.conf entry for host 172.17.0.2" - a new error, and a more specific one, since 172.17.0.2 is the container's actual IP on the docker bridge network. pg_hba.conf is what decides who's allowed to authenticate once they reach the server, separately from whether the server is listening at all. Added a rule scoped to 172.17.0.0/16 (the docker bridge subnet, not 0.0.0.0/0) requiring password auth, so any container on this host can attempt to log in with a password, but nothing outside the host can.

Even after adding that line the first retry still failed with the same error. Turned out to just be a stale reload - ran systemctl reload postgresql again along with SELECT pg_reload_conf() from psql to be sure, and the next attempt went through cleanly. Worth remembering that pg_hba.conf changes need an explicit reload to take effect, and it's easy to assume a change landed when it actually didn't.

End state: container reaches Postgres over the docker bridge network using host.docker.internal, Postgres listens on all interfaces but pg_hba.conf restricts who can actually authenticate to the docker subnet plus localhost, all with password auth except the local postgres superuser socket connection, which stays on peer auth since reaching that already requires host-level sudo access.

Confirmed working end to end with a real POST to /api/payments through the running container, not just the health check, since a health check passing doesn't prove writes work.
